GUIDE 04

Azure Container Apps and AKS with GitHub Actions

Two ways to run containers on Azure, each with a CI/CD pipeline: build, push to ACR, deploy, verify.

You wrote "ACS". Azure Container Service was retired and replaced by AKS (Azure Kubernetes Service), so this page covers AKS. If you meant something else, tell me and I'll change it.

ACA or AKS?

Azure Container AppsAKS
ModelServerless containers, Kubernetes hiddenManaged Kubernetes, you own workloads
ScalingBuilt-in, KEDA rules, scale to zeroHPA, cluster autoscaler, KEDA add-on
Ops effortLowHigher (nodes, upgrades, networking)
Best forAPIs, web apps, workers, jobsMany services, custom operators, full K8s control

Shared setup: ACR + OIDC login

az group create -n rg-uat -l centralindia
az acr create -n myacr -g rg-uat --sku Basic

For the passwordless GitHub-to-Azure login, follow the OIDC setup in the Terraform guide. The service principal needs AcrPush on the registry, plus rights on the target (Contributor on the resource group is the simple option).

az role assignment create --assignee $APP_ID --role AcrPush \
  --scope $(az acr show -n myacr --query id -o tsv)

Repository variables: AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_ID.

ACA: create and pipeline

One-time creation

az extension add --name containerapp --upgrade
az containerapp env create -n cae-uat -g rg-uat -l centralindia

az containerapp create -n myapp -g rg-uat --environment cae-uat \
  --image myacr.azurecr.io/myapp:latest \
  --registry-server myacr.azurecr.io --registry-identity system \
  --target-port 3000 --ingress external \
  --min-replicas 1 --max-replicas 5 \
  --cpu 0.5 --memory 1.0Gi

--registry-identity system lets the app pull from ACR through its managed identity, with no registry password. Grant that identity AcrPull if the CLI has not done so.

Pipeline

name: deploy-aca
on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

env:
  ACR: myacr
  APP: myapp
  RG: rg-uat

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: uat
    steps:
      - uses: actions/checkout@v4

      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Build and push
        run: |
          az acr login --name $ACR
          docker build -t $ACR.azurecr.io/$APP:${{ github.sha }} .
          docker push $ACR.azurecr.io/$APP:${{ github.sha }}

      - name: Deploy new revision
        run: |
          az containerapp update -n $APP -g $RG \
            --image $ACR.azurecr.io/$APP:${{ github.sha }} \
            --revision-suffix r${{ github.run_number }}

      - name: Smoke test
        run: |
          FQDN=$(az containerapp show -n $APP -g $RG --query properties.configuration.ingress.fqdn -o tsv)
          curl -fsS --retry 5 --retry-delay 5 https://$FQDN/health
Each update creates a new revision. In single-revision mode traffic moves once the new revision is healthy; in multiple-revision mode you can split traffic for canary releases.

AKS: create and pipeline

One-time creation

az aks create -n aks-uat -g rg-uat \
  --node-count 2 --node-vm-size Standard_B2s \
  --enable-managed-identity --enable-oidc-issuer --enable-workload-identity \
  --attach-acr myacr --generate-ssh-keys

az aks get-credentials -n aks-uat -g rg-uat

To let the pipeline run kubectl/helm, give the service principal Azure Kubernetes Service Cluster User Role plus RBAC rights inside the cluster (for example Azure Kubernetes Service RBAC Writer when Azure RBAC for Kubernetes is enabled).

Pipeline (plain manifests)

name: deploy-aks
on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

env:
  ACR: myacr
  APP: myapp
  AKS: aks-uat
  RG: rg-uat

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: uat
    steps:
      - uses: actions/checkout@v4

      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Build and push
        run: |
          az acr login --name $ACR
          docker build -t $ACR.azurecr.io/$APP:${{ github.sha }} .
          docker push $ACR.azurecr.io/$APP:${{ github.sha }}

      - uses: azure/aks-set-context@v4
        with:
          cluster-name: ${{ env.AKS }}
          resource-group: ${{ env.RG }}

      - name: Deploy manifests
        uses: azure/k8s-deploy@v5
        with:
          namespace: uat
          manifests: k8s/app.yaml
          images: ${{ env.ACR }}.azurecr.io/${{ env.APP }}:${{ github.sha }}
          strategy: basic

For Helm instead of raw manifests, use the helm upgrade --install ... --atomic job from the Kubernetes guide.

Operations: revisions, scaling, rollback

ACA

az containerapp revision list -n myapp -g rg-uat -o table
az containerapp revision activate   -n myapp -g rg-uat --revision myapp--r12
az containerapp ingress traffic set -n myapp -g rg-uat --revision-weight myapp--r12=100
az containerapp logs show -n myapp -g rg-uat --follow

# HTTP scale rule
az containerapp update -n myapp -g rg-uat --min-replicas 1 --max-replicas 10 \
  --scale-rule-name http --scale-rule-type http --scale-rule-http-concurrency 50

# env vars / secrets
az containerapp secret set -n myapp -g rg-uat --secrets db-pass=VALUE
az containerapp update -n myapp -g rg-uat --set-env-vars DB_PASS=secretref:db-pass

AKS

kubectl rollout undo deploy/myapp -n uat
kubectl autoscale deploy myapp -n uat --min=2 --max=10 --cpu-percent=70
az aks scale -n aks-uat -g rg-uat --node-count 3
az aks nodepool update -n aks-uat -g rg-uat --name nodepool1 --enable-cluster-autoscaler --min-count 2 --max-count 5

Cost notes (FinOps)

  • ACA: set min-replicas 0 on non-prod apps so idle ones cost close to nothing.
  • AKS: use the cluster autoscaler, right-size node SKUs from real CPU/memory usage, and stop UAT clusters out of hours with az aks stop / az aks start.
  • Set resource requests from observed usage. Over-requesting is the most common source of idle spend.
  • Tag resources (env, owner, app) and use Cost Management budgets with alerts.
