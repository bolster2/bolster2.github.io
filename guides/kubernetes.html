Fundamental concepts

The 24 terms to know before anything else, each with a command you will actually use.

#ConceptWhat it isHandy command
1PodSmallest unit in Kubernetes; wraps one or more containers with shared network and storage.kubectl get pods -o wide
2NodeA worker machine that runs pods, managed by the control plane.kubectl get nodes
3ClusterA group of nodes working together as a single Kubernetes system.kubectl cluster-info
4DeploymentManages the desired state of pods and handles rolling updates.kubectl rollout status deploy/myapp
5ReplicaSetKeeps a specific number of identical pods running at all times.kubectl get rs
6ServiceProvides stable networking to reach a group of pods reliably.kubectl get svc,endpoints
7IngressManages external HTTP/S access to services using host and path rules.kubectl get ingress
8ConfigMapStores non-sensitive configuration separately from container images.kubectl create configmap app-config --from-literal=LOG_LEVEL=info
9SecretStores sensitive data such as passwords and tokens (base64-encoded; enable encryption at rest).kubectl create secret generic db --from-literal=password=VALUE
10NamespaceLogical partition of cluster resources for isolation and organisation.kubectl get ns
11KubeletNode agent that makes sure the containers described in pods are running.systemctl status kubelet (on a node)
12kubectlCLI tool to interact with and manage Kubernetes clusters.kubectl config get-contexts
13Control PlaneThe components that manage the overall cluster state (API server, scheduler, controller manager, etcd).kubectl get pods -n kube-system
14SchedulerAssigns new pods to suitable nodes based on resource needs and policies.kubectl describe pod X (see Events)
15Controller ManagerRuns background controllers to maintain cluster state automatically.kubectl get pods -n kube-system | grep controller
16etcdDistributed key-value store that persists all cluster data. Back it up on self-managed clusters.etcdctl snapshot save backup.db
17Taints & TolerationsControl which pods are allowed to run on specific nodes.kubectl taint nodes node1 dedicated=db:NoSchedule
18Labels & SelectorsUsed to group and select Kubernetes objects dynamically.kubectl get pods -l app=myapp
19Resource Requests & LimitsDefine how much CPU and memory a container needs and can use.kubectl top pods
20HelmKubernetes package manager for deploying and managing applications.helm upgrade --install myapp ./mychart
21CRD (Custom Resource Definition)Lets you define your own Kubernetes resource types.kubectl get crd
22OperatorA controller built to automate complex application operations using CRDs.kubectl get pods -n operators
23DaemonSetRuns a pod on every node, or on specific nodes, in the cluster.kubectl get ds -A
24Logs & EventsHelp you debug and track what is happening inside the cluster.kubectl logs POD and kubectl get events --sort-by=.lastTimestamp

How the pieces fit

You (kubectl / Helm)
      |
      v
Control Plane: API server -> etcd (state)
      |            Scheduler (picks a node) + Controller Manager (keeps desired state)
      v
Nodes: kubelet runs Pods
      |
Deployment -> ReplicaSet -> Pods  <-- Service (stable IP) <-- Ingress (HTTP/S from outside)
                              |
                  ConfigMap / Secret / Requests & Limits

KIND cluster

KIND (Kubernetes IN Docker) runs cluster nodes as containers. Needs Docker, kubectl and kind.

# Linux / WSL
curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.23.0/kind-linux-amd64
chmod +x ./kind && sudo mv ./kind /usr/local/bin/kind
# Windows: winget install Kubernetes.kind
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    kubeadmConfigPatches:
      - |
        kind: InitConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "ingress-ready=true"
    extraPortMappings:
      - containerPort: 80
        hostPort: 8080
        protocol: TCP
      - containerPort: 443
        hostPort: 8443
        protocol: TCP
  - role: worker
  - role: worker
kind create cluster --name dev --config kind-config.yaml
kubectl cluster-info --context kind-dev
kubectl get nodes

# load a locally built image into the cluster (no registry needed)
docker build -t myapp:dev .
kind load docker-image myapp:dev --name dev

kind delete cluster --name dev

Plain manifest deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 2
  selector:
    matchLabels: { app: myapp }
  template:
    metadata:
      labels: { app: myapp }
    spec:
      containers:
        - name: myapp
          image: myapp:dev
          ports: [{ containerPort: 3000 }]
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { cpu: 500m, memory: 256Mi }
          readinessProbe:
            httpGet: { path: /health, port: 3000 }
          livenessProbe:
            httpGet: { path: /health, port: 3000 }
            initialDelaySeconds: 10
---
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  selector: { app: myapp }
  ports: [{ port: 80, targetPort: 3000 }]
kubectl apply -f k8s/app.yaml
kubectl rollout status deploy/myapp
kubectl port-forward svc/myapp 8081:80

Helm chart

helm create mychart     # scaffold
mychart/
  Chart.yaml
  values.yaml
  values-uat.yaml  values-prod.yaml    # your overrides
  templates/
    deployment.yaml  service.yaml  ingress.yaml  _helpers.tpl
replicaCount: 2
image:
  repository: myacr.azurecr.io/myapp
  tag: "latest"
  pullPolicy: IfNotPresent
service:
  port: 80
containerPort: 3000
resources:
  requests: { cpu: 100m, memory: 128Mi }
  limits:   { cpu: 500m, memory: 256Mi }
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          ports:
            - containerPort: {{ .Values.containerPort }}
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
helm lint mychart
helm template mychart -f mychart/values-uat.yaml        # render without installing
helm upgrade --install myapp mychart -n uat --create-namespace -f mychart/values-uat.yaml --set image.tag=1.4.2 --atomic --wait
helm history myapp -n uat
helm rollback myapp 1 -n uat
--atomic rolls back automatically if the release fails. helm upgrade --install is idempotent, so one command serves first install and every update.

CI: test the chart on KIND in GitHub Actions

Every PR builds the image, spins up a throwaway KIND cluster inside the runner, installs the chart, and checks it is healthy.

name: ci
on:
  pull_request:
  push:
    branches: [main]

jobs:
  test-chart:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: azure/setup-helm@v4

      - name: Lint chart
        run: helm lint mychart

      - name: Build image
        run: docker build -t myapp:${{ github.sha }} .

      - name: Create KIND cluster
        uses: helm/kind-action@v1
        with:
          cluster_name: ci

      - name: Load image into KIND
        run: kind load docker-image myapp:${{ github.sha }} --name ci

      - name: Install chart
        run: |
          helm upgrade --install myapp mychart \
            --set image.repository=myapp \
            --set image.tag=${{ github.sha }} \
            --set image.pullPolicy=Never \
            --wait --timeout 120s

      - name: Smoke test
        run: |
          kubectl rollout status deploy/myapp --timeout=90s
          kubectl get pods -o wide
          kubectl port-forward svc/myapp 8081:80 &
          sleep 3
          curl -fsS http://localhost:8081/health

CD: release with Helm

On merge to main: build and push the image to ACR, then helm upgrade against AKS. Azure login uses OIDC (see the Terraform guide for setup).

name: cd
on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

env:
  ACR: myacr
  IMAGE: myapp
  AKS: aks-uat
  RG: rg-uat

jobs:
  release:
    runs-on: ubuntu-latest
    environment: uat
    steps:
      - uses: actions/checkout@v4

      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Build and push image
        run: |
          az acr login --name $ACR
          docker build -t $ACR.azurecr.io/$IMAGE:${{ github.sha }} .
          docker push $ACR.azurecr.io/$IMAGE:${{ github.sha }}

      - uses: azure/aks-set-context@v4
        with:
          cluster-name: ${{ env.AKS }}
          resource-group: ${{ env.RG }}

      - uses: azure/setup-helm@v4

      - name: Deploy
        run: |
          helm upgrade --install myapp mychart \
            -n uat --create-namespace \
            -f mychart/values-uat.yaml \
            --set image.repository=$ACR.azurecr.io/$IMAGE \
            --set image.tag=${{ github.sha }} \
            --atomic --wait --timeout 5m
The AKS cluster must be able to pull from ACR: az aks update -n aks-uat -g rg-uat --attach-acr myacr.

10 Kubernetes production issues

Symptoms, possible causes and the first checks to run.

IssueWhat you see / possible causesFirst checks
CrashLoopBackOffRepeated restarts. App errors, bad config or failed probes.Read previous logs; inspect exit reason and events.
kubectl logs POD --previous
ImagePullBackOffImage cannot be pulled. Wrong tag, registry auth or connectivity.Check image name, pull secrets and pod events. On AKS verify --attach-acr; on KIND use kind load.
Pod PendingPod not ready to run. Scheduling or storage constraints.Check events, requests, taints, affinity and PVCs.
kubectl describe pod POD
Service unreachableConnection refused or timeout. Selector, port or readiness mismatch.Check labels, targetPort, EndpointSlices and NetworkPolicies.
kubectl get endpointslices -l kubernetes.io/service-name=SVC
Ingress 502/503Gateway errors. Backend or routing problems.Check controller logs, Service ports and ready backends.
OOMKilledContainer killed for memory. Limit hit or node memory pressure.Inspect termination reason, memory usage and node events.
kubectl describe pod POD (Last State: OOMKilled)
Node NotReadyNode unhealthy. Kubelet, runtime or network issue.Describe node; inspect conditions and kubelet logs.
journalctl -u kubelet on the node
PVC PendingStorage claim not bound. Class, capacity or provisioning issue.Describe PVC; check StorageClass, CSI and binding mode.
DNS failureService names do not resolve. DNS config or connectivity issue.Test DNS inside a pod; check CoreDNS and DNS traffic.
High CPU / MemorySlow responses or resource pressure. Load or application issue.Check metrics, throttling, requests, limits and app profiles.
kubectl top pods

Start with evidence

kubectl describe pod <pod> -n <ns>
kubectl logs <pod> -n <ns> -c <container> --previous
kubectl get events -n <ns> --sort-by=.metadata.creationTimestamp
kubectl top pods -n <ns>

Issue-specific commands

# exit code and last state (137 = killed, often OOM)
kubectl get pod POD -n NS -o jsonpath='{.status.containerStatuses[0].lastState}'
kubectl describe pod POD -n NS | grep -A6 "Last State"
# probe settings
kubectl get pod POD -n NS -o yaml | grep -A8 -E "livenessProbe|readinessProbe"
kubectl describe pod POD -n NS | grep -A10 Events
kubectl get pod POD -n NS -o jsonpath='{.spec.containers[*].image}'
kubectl get secret -n NS                      # is the pull secret there?

kubectl describe pod POD -n NS               # look for FailedScheduling
kubectl describe nodes | grep -A5 -E "Taints|Allocated resources"

kubectl get hpa -n NS

Other useful commands

kubectl exec -it POD -n NS -- sh
kubectl get events -A --sort-by=.lastTimestamp | tail -30
helm status RELEASE -n NS && helm history RELEASE -n NS     # Helm stuck? then: helm rollback RELEASE REV
Rule of thumb: events first, then logs, then metrics. Most issues name themselves in kubectl describe within the first 20 lines of Events.
