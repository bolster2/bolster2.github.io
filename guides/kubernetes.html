Fundamental concepts

The 24 terms to know before anything else, each with a command you will actually use.

KIND cluster

KIND (Kubernetes IN Docker) runs cluster nodes as containers. Needs Docker, kubectl and kind.

# Linux / WSL
curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.23.0/kind-linux-amd64
chmod +x ./kind && sudo mv ./kind /usr/local/bin/kind
# Windows: winget install Kubernetes.kind
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    kubeadmConfigPatches:
      - |
        kind: InitConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "ingress-ready=true"
    extraPortMappings:
      - containerPort: 80
        hostPort: 8080
        protocol: TCP
      - containerPort: 443
        hostPort: 8443
        protocol: TCP
  - role: worker
  - role: worker
kind create cluster --name dev --config kind-config.yaml
kubectl cluster-info --context kind-dev
kubectl get nodes

# load a locally built image into the cluster (no registry needed)
docker build -t myapp:dev .
kind load docker-image myapp:dev --name dev

kind delete cluster --name dev

Plain manifest deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 2
  selector:
    matchLabels: { app: myapp }
  template:
    metadata:
      labels: { app: myapp }
    spec:
      containers:
        - name: myapp
          image: myapp:dev
          ports: [{ containerPort: 3000 }]
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { cpu: 500m, memory: 256Mi }
          readinessProbe:
            httpGet: { path: /health, port: 3000 }
          livenessProbe:
            httpGet: { path: /health, port: 3000 }
            initialDelaySeconds: 10
---
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  selector: { app: myapp }
  ports: [{ port: 80, targetPort: 3000 }]
kubectl apply -f k8s/app.yaml
kubectl rollout status deploy/myapp
kubectl port-forward svc/myapp 8081:80

Helm chart

helm create mychart     # scaffold
mychart/
  Chart.yaml
  values.yaml
  values-uat.yaml  values-prod.yaml    # your overrides
  templates/
    deployment.yaml  service.yaml  ingress.yaml  _helpers.tpl
replicaCount: 2
image:
  repository: myacr.azurecr.io/myapp
  tag: "latest"
  pullPolicy: IfNotPresent
service:
  port: 80
containerPort: 3000
resources:
  requests: { cpu: 100m, memory: 128Mi }
  limits:   { cpu: 500m, memory: 256Mi }
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          ports:
            - containerPort: {{ .Values.containerPort }}
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
helm lint mychart
helm template mychart -f mychart/values-uat.yaml        # render without installing
helm upgrade --install myapp mychart -n uat --create-namespace -f mychart/values-uat.yaml --set image.tag=1.4.2 --atomic --wait
helm history myapp -n uat
helm rollback myapp 1 -n uat
--atomic rolls back automatically if the release fails. helm upgrade --install is idempotent, so one command serves first install and every update.

CI: test the chart on KIND in GitHub Actions

Every PR builds the image, spins up a throwaway KIND cluster inside the runner, installs the chart, and checks it is healthy.

name: ci
on:
  pull_request:
  push:
    branches: [main]

jobs:
  test-chart:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: azure/setup-helm@v4

      - name: Lint chart
        run: helm lint mychart

      - name: Build image
        run: docker build -t myapp:${{ github.sha }} .

      - name: Create KIND cluster
        uses: helm/kind-action@v1
        with:
          cluster_name: ci

      - name: Load image into KIND
        run: kind load docker-image myapp:${{ github.sha }} --name ci

      - name: Install chart
        run: |
          helm upgrade --install myapp mychart \
            --set image.repository=myapp \
            --set image.tag=${{ github.sha }} \
            --set image.pullPolicy=Never \
            --wait --timeout 120s

      - name: Smoke test
        run: |
          kubectl rollout status deploy/myapp --timeout=90s
          kubectl get pods -o wide
          kubectl port-forward svc/myapp 8081:80 &
          sleep 3
          curl -fsS http://localhost:8081/health

CD: release with Helm

On merge to main: build and push the image to ACR, then helm upgrade against AKS. Azure login uses OIDC (see the Terraform guide for setup).

name: cd
on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

env:
  ACR: myacr
  IMAGE: myapp
  AKS: aks-uat
  RG: rg-uat

jobs:
  release:
    runs-on: ubuntu-latest
    environment: uat
    steps:
      - uses: actions/checkout@v4

      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Build and push image
        run: |
          az acr login --name $ACR
          docker build -t $ACR.azurecr.io/$IMAGE:${{ github.sha }} .
          docker push $ACR.azurecr.io/$IMAGE:${{ github.sha }}

      - uses: azure/aks-set-context@v4
        with:
          cluster-name: ${{ env.AKS }}
          resource-group: ${{ env.RG }}

      - uses: azure/setup-helm@v4

      - name: Deploy
        run: |
          helm upgrade --install myapp mychart \
            -n uat --create-namespace \
            -f mychart/values-uat.yaml \
            --set image.repository=$ACR.azurecr.io/$IMAGE \
            --set image.tag=${{ github.sha }} \
            --atomic --wait --timeout 5m
The AKS cluster must be able to pull from ACR: az aks update -n aks-uat -g rg-uat --attach-acr myacr.

Symptoms, possible causes and the first checks to run.

Top 7 troubleshooting use cases

Each case follows the same shape: symptoms, likely causes, a step-by-step process, then the fix.

#Use caseWhere it happens
1Node Not ReadyNode
2Node Disk PressureNode
3CreateContainerErrorContainer runtime
4CreateContainerConfigErrorPod config
5ImagePullBackOffImage pull
6RunContainerErrorContainer start
7OOMKilledMemory
Order of the pod lifecycle helps you place the error: pull image (ImagePullBackOff) → validate config (CreateContainerConfigError) → create container (CreateContainerError) → start process (RunContainerError, CrashLoopBackOff) → run (OOMKilled). The status tells you which step failed.

1. How to fix Node Not Ready

Symptoms: kubectl get nodes shows NotReady; pods on it become Unknown or get evicted after about 5 minutes.

Likely causes: kubelet stopped or crashed, container runtime down, network or CNI failure, node out of disk or memory, expired certificates, the VM stopped or lost connectivity to the API server.

  1. See which node and why: kubectl get nodes, then look at the Conditions block (Ready, MemoryPressure, DiskPressure, PIDPressure, NetworkUnavailable).
  2. Read the node events for the reason (for example "Kubelet stopped posting node status").
  3. Log in to the node and check kubelet and the runtime.
  4. Check resources: disk, memory, and the CNI pods running on that node.
  5. Fix the cause. If the node cannot be recovered, replace it.
kubectl get nodes -o wide
kubectl describe node NODE | grep -A12 Conditions
kubectl get events --field-selector involvedObject.name=NODE --sort-by=.lastTimestamp

# on the node
systemctl status kubelet containerd
journalctl -u kubelet --since "30 min ago" --no-pager | tail -50
df -h; free -m
crictl ps                          # runtime responding?

# CNI / networking pods on that node
kubectl get pods -n kube-system -o wide --field-selector spec.nodeName=NODE

Fix:

# restart services
sudo systemctl restart containerd
sudo systemctl restart kubelet

# free disk if full (see use case 2)
# if the node cannot be recovered: move work off it, then replace it
kubectl cordon NODE
kubectl drain NODE --ignore-daemonsets --delete-emptydir-data
kubectl delete node NODE           # self-managed: re-join a new node

# AKS: reimage or scale the pool instead of fixing by hand
az aks nodepool scale -g rg-uat --cluster-name aks-uat -n nodepool1 --node-count 3
# or reimage the bad VM instance in the node resource group (MC_*)
# az vmss list-instances -g MC_RG -n VMSS_NAME -o table
# az vmss reimage -g MC_RG -n VMSS_NAME --instance-id ID
On AKS and other managed services, prefer replacing the node (scale up, cordon and drain, delete the bad one) over repairing it in place.

2. How to fix Node Disk Pressure

Symptoms: node condition DiskPressure=True, taint node.kubernetes.io/disk-pressure, new pods will not schedule there, and running pods are Evicted.

Likely causes: accumulated container images, large container logs, emptyDir volumes or pod writes to the container filesystem, system logs in /var/log, a too-small OS disk. By default the kubelet starts evicting when free space on the node's filesystem drops below about 10% (and about 15% on the image filesystem).

  1. Confirm the condition on the node.
  2. Find what is using the space on the node.
  3. Free space safely: unused images, old logs, evicted pods.
  4. Prevent a repeat: limits, log rotation, bigger disk.
kubectl describe node NODE | grep -E "DiskPressure|ephemeral-storage"
kubectl get pods -A --field-selector=status.phase=Failed     # evicted pods

# on the node
df -hT
sudo du -xh /var --max-depth=2 2>/dev/null | sort -rh | head -15
sudo du -sh /var/lib/containerd /var/log/pods /var/log/containers 2>/dev/null
crictl images
crictl imagefsinfo

Fix:

# remove unused images
sudo crictl rmi --prune

# trim system logs
sudo journalctl --vacuum-size=200M

# delete leftover evicted pods
kubectl delete pods -A --field-selector=status.phase=Failed

# the pressure condition clears on its own once space is free and the kubelet re-evaluates

Prevent it: set ephemeral-storage requests and limits, rotate container logs, and size node disks for your images and logs.

resources:
  requests:
    ephemeral-storage: "500Mi"
  limits:
    ephemeral-storage: "2Gi"
containerLogMaxSize: 50Mi
containerLogMaxFiles: 5

3. Understanding CreateContainerError

Symptoms: pod status CreateContainerError. The image was pulled, but the runtime failed to create the container.

Likely causes: the image has no ENTRYPOINT/CMD and the pod does not set command; the container name already exists on the node; a volume or subPath could not be mounted; invalid securityContext; runtime problems on the node.

  1. Read the exact error in the pod events.
  2. Check the container state message.
  3. Compare the pod spec (command, args, volumes, securityContext) with the image.
  4. If the message points at the runtime, check containerd on the node.
kubectl describe pod POD -n NS | grep -A15 Events
kubectl get pod POD -n NS -o jsonpath='{.status.containerStatuses[*].state.waiting.message}'
kubectl get pod POD -n NS -o yaml | grep -A12 -E "command|args|volumeMounts|securityContext"

# does the image define a command?
docker inspect IMAGE --format '{{.Config.Entrypoint}} {{.Config.Cmd}}'

# on the node
journalctl -u containerd --since "15 min ago" --no-pager | tail -40

Fix by message:

Message containsFix
no command specifiedAdd command/args to the pod, or fix the Dockerfile CMD.
name is already in useRestart the pod; if it repeats, restart containerd on the node.
failed to mount / subPathFix the volume or the path it points at; make sure the file or directory exists.
runAsUser / security context errorsCorrect securityContext values to match the image and cluster policy.

4. Understanding CreateContainerConfigError

Symptoms: pod status CreateContainerConfigError. Kubernetes could not build the container's configuration, so the container never started.

Likely causes: a referenced ConfigMap or Secret does not exist, a key is missing from it, it lives in a different namespace, or the image runs as root while the pod sets runAsNonRoot: true.

  1. kubectl describe pod. The Events line names the exact thing missing, for example secret "db" not found or couldn't find key password in Secret.
  2. List the ConfigMaps and Secrets in the same namespace.
  3. Check the key names for typos (they are case-sensitive).
  4. Create or correct the object. The pod retries by itself.
kubectl describe pod POD -n NS | grep -A10 Events
kubectl get configmap,secret -n NS
kubectl get secret db -n NS -o jsonpath='{.data}' | head -c 300
kubectl get pod POD -n NS -o yaml | grep -B2 -A6 -E "configMapKeyRef|secretKeyRef|envFrom"

Fix:

kubectl create secret generic db -n NS --from-literal=password=VALUE
kubectl create configmap app-config -n NS --from-literal=LOG_LEVEL=info
# the pod picks them up on its next retry; or: kubectl delete pod POD -n NS
env:
  - name: FEATURE_FLAG
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: FEATURE_FLAG
        optional: true          # pod starts even if it is missing
For the runAsNonRoot case, either set a numeric user in the Dockerfile (USER 1000) or set runAsUser: 1000 in the pod's securityContext. A non-numeric USER node can fail this check, so a numeric ID is safer.

5. Understanding ImagePullBackOff

Symptoms: ErrImagePull first, then ImagePullBackOff as Kubernetes retries with growing delays.

Likely causes: wrong image name or tag, private registry without credentials, expired token, registry rate limit (Docker Hub), network, DNS or firewall blocking the registry, or an image built for a different CPU architecture.

  1. Read the pull error in the events. It names the cause.
  2. Confirm the image and tag exist in the registry.
  3. Confirm the cluster has credentials for that registry.
  4. Test the pull from the node itself.
Error textMeaning and fix
manifest unknown / not foundTag or repository name is wrong. Correct it in the manifest.
unauthorized / authentication requiredMissing or wrong credentials. Add imagePullSecrets or attach ACR.
toomanyrequestsDocker Hub rate limit. Authenticate, or mirror the image into your ACR.
i/o timeout / no such hostNetwork or DNS egress problem from the node.
no matching manifest for linux/amd64Image built for another architecture. Rebuild for the node's platform.
kubectl describe pod POD -n NS | grep -A10 Events
kubectl get pod POD -n NS -o jsonpath='{.spec.containers[*].image}'

# does the tag exist?  (ACR)
az acr repository show-tags -n myacr --repository myapp -o table
# can the cluster pull from ACR?
az aks check-acr -n aks-uat -g rg-uat --acr myacr.azurecr.io

# test a pull directly on the node
sudo crictl pull myacr.azurecr.io/myapp:1.0

Fix:

# AKS + ACR (no secret needed)
az aks update -n aks-uat -g rg-uat --attach-acr myacr

# any other private registry
kubectl create secret docker-registry regcred -n NS \
  --docker-server=REGISTRY --docker-username=USER --docker-password=PASSWORD
# then reference it:
#   spec:
#     imagePullSecrets:
#       - name: regcred

# KIND (local images are not in a registry)
kind load docker-image myapp:dev --name dev

6. Understanding RunContainerError

Symptoms: pod status RunContainerError. The container was created, but the runtime could not start its process.

Likely causes: the command or entrypoint file does not exist in the image (executable file not found in $PATH), the script is not executable or has Windows line endings, wrong CPU architecture (exec format error), a volume mount that fails, or a bad securityContext.

  1. Read the exact start error from the events or the container state.
  2. Run the same image locally with the same command to reproduce it.
  3. Check that the file exists, is executable, and has the right interpreter line.
  4. Check the image architecture and the mounts.
kubectl describe pod POD -n NS | grep -A12 -E "State|Events"
kubectl get pod POD -n NS -o jsonpath='{.status.containerStatuses[*].state}'

# reproduce
docker run --rm -it --entrypoint sh IMAGE
ls -l /app/start.sh; head -1 /app/start.sh          # interpreter line, exec bit

# architecture of the image
docker image inspect IMAGE --format '{{.Architecture}}'
kubectl get nodes -o jsonpath='{.items[*].status.nodeInfo.architecture}'
Message containsFix
executable file not foundUse the correct path in command; install the binary in the image.
permission deniedchmod +x the script in the Dockerfile, and check the user.
no such file or directory (on a script)Fix the shebang, or convert CRLF to LF (dos2unix).
exec format errorBuild for the node's architecture: docker buildx build --platform linux/amd64.
COPY start.sh /app/start.sh
RUN chmod +x /app/start.sh && sed -i 's/\r$//' /app/start.sh
ENTRYPOINT ["/app/start.sh"]

Use kubectl debug to get a shell next to a failing pod when you cannot reproduce it locally:

kubectl debug -it POD -n NS --image=busybox:1.36 --target=CONTAINER

7. Understanding OOMKilled

Symptoms: container restarts, Last State: Terminated, Reason: OOMKilled, Exit Code: 137, often followed by CrashLoopBackOff.

Likely causes: the memory limit is lower than what the app needs, a memory leak, a runtime that ignores the container limit (JVM or Node heap), a traffic spike, or the node itself running out of memory so the kernel kills a process.

  1. Confirm the reason and exit code 137 in the pod description.
  2. Decide: is it the container limit or a node-wide shortage? (Node events and kubectl top nodes tell you.)
  3. Look at actual usage against the limit.
  4. Fix the limit, the app memory settings, or the leak, in that order of effort.
kubectl describe pod POD -n NS | grep -A8 "Last State"
kubectl get pod POD -n NS -o jsonpath='{.status.containerStatuses[0].lastState.terminated}'
kubectl top pod POD -n NS --containers
kubectl top nodes
kubectl get events -n NS --sort-by=.lastTimestamp | grep -i -E "oom|evict"

# on the node: kernel OOM log
sudo dmesg -T | grep -i -E "oom|killed process"

Fix:

resources:
  requests:
    memory: "256Mi"
  limits:
    memory: "512Mi"     # set above the observed peak, with headroom
# Java: size the heap from the container limit
env:
  - name: JAVA_TOOL_OPTIONS
    value: "-XX:MaxRAMPercentage=75.0"

# Node.js: keep the heap below the container limit (value in MB)
env:
  - name: NODE_OPTIONS
    value: "--max-old-space-size=384"
  • If usage climbs steadily and never drops, it is a leak. Profile the app instead of raising limits again.
  • If many pods hit the limit at once, check the HPA and for a traffic spike.
  • For node-level OOM, add nodes or move heavy pods, and always set requests so the scheduler places pods properly.

Quick decision flow

kubectl get pod POD -n NS          # read STATUS
  |
  |- ImagePullBackOff / ErrImagePull       -> use case 5  (image / registry)
  |- CreateContainerConfigError            -> use case 4  (missing ConfigMap/Secret/key)
  |- CreateContainerError                  -> use case 3  (runtime could not create it)
  |- RunContainerError                     -> use case 6  (process could not start)
  |- CrashLoopBackOff + exit 137 / OOM     -> use case 7  (memory)
  |- Pod Pending / Evicted                 -> use case 2  (node disk pressure) or scheduling
  `- Pods Unknown, node NotReady           -> use case 1  (node health)
