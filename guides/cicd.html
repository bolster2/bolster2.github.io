Repo layout and the pipeline stages

repo/
  apps/
    node-api/      package.json  server.js  Dockerfile
    java-service/  pom.xml  src/  Dockerfile
  .github/workflows/
    node-api.yml  java-service.yml  ci-multi.yml
  Jenkinsfile

Every pipeline below follows the same stages, so you can reason about them the same way:

  1. Checkout the code
  2. Install + test (npm ci && npm test or mvn verify)
  3. Build the image and tag it with the commit SHA
  4. Push to the registry (ACR)
  5. Deploy to UAT automatically, to Production after approval
  6. Smoke test the health endpoint
Tag images with the commit SHA, never only latest. It makes every deployment traceable and rollback a one-liner. Docker basics are on the Docker page.

GitHub Actions: Node.js app

Tests with npm, builds and pushes an image to ACR, and updates an Azure Container App. Azure login uses OIDC, with no stored password (setup in the Terraform guide).

name: node-api
on:
  push:
    branches: [main]
    paths: ["apps/node-api/**"]
  pull_request:
    paths: ["apps/node-api/**"]

permissions:
  id-token: write
  contents: read

env:
  ACR: myacr
  APP: node-api
  RG: rg-uat

defaults:
  run:
    working-directory: apps/node-api

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: [18, 20]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm
          cache-dependency-path: apps/node-api/package-lock.json
      - run: npm ci
      - run: npm run lint --if-present
      - run: npm test --if-present

  deploy-uat:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: uat
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - name: Build and push
        run: |
          az acr login --name $ACR
          docker build -t $ACR.azurecr.io/$APP:${{ github.sha }} .
          docker push $ACR.azurecr.io/$APP:${{ github.sha }}
      - name: Deploy
        run: |
          az containerapp update -n $APP -g $RG \
            --image $ACR.azurecr.io/$APP:${{ github.sha }}
      - name: Smoke test
        run: |
          FQDN=$(az containerapp show -n $APP -g $RG --query properties.configuration.ingress.fqdn -o tsv)
          curl -fsS --retry 5 --retry-delay 5 https://$FQDN/health

  deploy-prod:
    needs: deploy-uat
    runs-on: ubuntu-latest
    environment: production        # set required reviewers on this environment
    steps:
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - name: Promote the same image to prod
        run: |
          az containerapp update -n $APP-prod -g rg-prod \
            --image $ACR.azurecr.io/$APP:${{ github.sha }}
The prod job reuses the image already built and tested for UAT, so what you approved is what ships. Put required reviewers on the production environment in repo Settings, then Environments. For production the registry should be reachable from that environment's identity (grant AcrPull).

GitHub Actions: Maven app

name: java-service
on:
  push:
    branches: [main]
    paths: ["apps/java-service/**"]
  pull_request:
    paths: ["apps/java-service/**"]

permissions:
  id-token: write
  contents: read
  checks: write

env:
  ACR: myacr
  APP: java-service
  RG: rg-uat
  AKS: aks-uat

defaults:
  run:
    working-directory: apps/java-service

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 17
          cache: maven
      - name: Build and test
        run: mvn -B verify
      - name: Publish test report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: surefire-reports
          path: apps/java-service/target/surefire-reports
      - name: Keep the jar
        uses: actions/upload-artifact@v4
        with:
          name: app-jar
          path: apps/java-service/target/*.jar

  deploy-uat:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: uat
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with:
          name: app-jar
          path: apps/java-service/target
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - name: Build and push image
        run: |
          az acr login --name $ACR
          docker build -t $ACR.azurecr.io/$APP:${{ github.sha }} .
          docker push $ACR.azurecr.io/$APP:${{ github.sha }}
      - uses: azure/aks-set-context@v4
        with:
          cluster-name: ${{ env.AKS }}
          resource-group: ${{ env.RG }}
      - name: Deploy to AKS
        uses: azure/k8s-deploy@v5
        with:
          namespace: uat
          manifests: apps/java-service/k8s/deployment.yaml
          images: ${{ env.ACR }}.azurecr.io/${{ env.APP }}:${{ github.sha }}
# ---- build ----
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B package -DskipTests

# ---- runtime ----
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar
RUN addgroup -S app && adduser -S app -G app
USER app
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

The workflow above also uploads the jar built by Maven, but the Dockerfile rebuilds it in its own stage. Keep one or the other as your source of truth. The multi-stage Dockerfile is simpler and is enough on its own.

No containers? Deploy the jar to a Linux VM

- name: Copy jar and restart
  run: |
    install -m 600 /dev/null key.pem
    echo "${{ secrets.VM_SSH_KEY }}" > key.pem
    scp -i key.pem -o StrictHostKeyChecking=accept-new target/app.jar deploy@${{ vars.VM_HOST }}:/opt/app/app.jar
    ssh -i key.pem deploy@${{ vars.VM_HOST }} "sudo systemctl restart java-service"
    rm -f key.pem

GitHub Actions: many apps in one repo

One workflow detects which apps changed and builds only those, using a matrix.

name: ci-multi
on:
  push:
    branches: [main]
  pull_request:

jobs:
  changes:
    runs-on: ubuntu-latest
    outputs:
      apps: ${{ steps.filter.outputs.changes }}
    steps:
      - uses: actions/checkout@v4
      - id: filter
        uses: dorny/paths-filter@v3
        with:
          filters: |
            node-api:
              - 'apps/node-api/**'
            java-service:
              - 'apps/java-service/**'

  build:
    needs: changes
    if: needs.changes.outputs.apps != '[]'
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        app: ${{ fromJSON(needs.changes.outputs.apps) }}
    steps:
      - uses: actions/checkout@v4

      - name: Node app
        if: matrix.app == 'node-api'
        working-directory: apps/node-api
        run: |
          npm ci
          npm test --if-present

      - name: Java app
        if: matrix.app == 'java-service'
        working-directory: apps/java-service
        run: mvn -B verify

      - name: Build image
        run: docker build -t ${{ matrix.app }}:${{ github.sha }} apps/${{ matrix.app }}
The Java step needs a JDK. GitHub's Ubuntu runners include Java and Maven, but pin a version with actions/setup-java if you need a specific one.

Reusable workflow (no copy-paste)

Put the shared build and deploy logic in one workflow and call it once per app.

name: deploy-app
on:
  workflow_call:
    inputs:
      app:
        type: string
        required: true
      path:
        type: string
        required: true
      environment:
        type: string
        required: true

permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - name: Build and push
        run: |
          az acr login --name myacr
          docker build -t myacr.azurecr.io/${{ inputs.app }}:${{ github.sha }} ${{ inputs.path }}
          docker push myacr.azurecr.io/${{ inputs.app }}:${{ github.sha }}
      - name: Deploy
        run: |
          az containerapp update -n ${{ inputs.app }} -g rg-${{ inputs.environment }} \
            --image myacr.azurecr.io/${{ inputs.app }}:${{ github.sha }}
name: release
on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  node-api:
    uses: ./.github/workflows/deploy-app.yml
    with:
      app: node-api
      path: apps/node-api
      environment: uat
    secrets: inherit

  java-service:
    uses: ./.github/workflows/deploy-app.yml
    with:
      app: java-service
      path: apps/java-service
      environment: uat
    secrets: inherit

Adding a third app is now one more short job block.

Jenkinsfile: Node.js app

Declarative pipeline. Jenkins runs the build inside a Node container so the agent needs only Docker.

pipeline {
  agent none

  options {
    timestamps()
    disableConcurrentBuilds()
    timeout(time: 30, unit: 'MINUTES')
    buildDiscarder(logRotator(numToKeepStr: '20'))
  }

  environment {
    ACR   = 'myacr'
    APP   = 'node-api'
    IMAGE = "${ACR}.azurecr.io/${APP}:${BUILD_NUMBER}"
  }

  stages {
    stage('Test') {
      agent { docker { image 'node:20-alpine' } }
      steps {
        sh 'npm ci'
        sh 'npm run lint --if-present'
        sh 'npm test --if-present'
      }
    }

    stage('Build and push image') {
      agent any
      when { branch 'main' }
      steps {
        withCredentials([usernamePassword(credentialsId: 'azure-sp',
                         usernameVariable: 'AZ_ID', passwordVariable: 'AZ_SECRET')]) {
          sh '''
            az login --service-principal -u "$AZ_ID" -p "$AZ_SECRET" --tenant "$AZ_TENANT" --output none
            az acr login --name "$ACR"
            docker build -t "$IMAGE" .
            docker push "$IMAGE"
          '''
        }
      }
    }

    stage('Deploy UAT') {
      agent any
      when { branch 'main' }
      steps {
        withCredentials([usernamePassword(credentialsId: 'azure-sp',
                         usernameVariable: 'AZ_ID', passwordVariable: 'AZ_SECRET')]) {
          sh '''
            az login --service-principal -u "$AZ_ID" -p "$AZ_SECRET" --tenant "$AZ_TENANT" --output none
            az containerapp update -n "$APP" -g rg-uat --image "$IMAGE"
          '''
        }
      }
    }

    stage('Approve production') {
      when { branch 'main' }
      steps {
        timeout(time: 1, unit: 'HOURS') {
          input message: 'Deploy to production?', ok: 'Deploy'
        }
      }
    }

    stage('Deploy production') {
      agent any
      when { branch 'main' }
      steps {
        withCredentials([usernamePassword(credentialsId: 'azure-sp',
                         usernameVariable: 'AZ_ID', passwordVariable: 'AZ_SECRET')]) {
          sh '''
            az login --service-principal -u "$AZ_ID" -p "$AZ_SECRET" --tenant "$AZ_TENANT" --output none
            az containerapp update -n "$APP-prod" -g rg-prod --image "$IMAGE"
          '''
        }
      }
    }
  }

  post {
    success { echo "Deployed ${IMAGE}" }
    failure { echo 'Build failed. Check the stage logs.' }
    always  { cleanWs() }
  }
}
Set AZ_TENANT as a global environment variable in Jenkins (or add it to the environment block). Store the service principal as a Username with password credential with ID azure-sp: the app ID as username and the client secret as password. Never print secrets, and avoid Groovy string interpolation of secrets: single-quoted ''' shell blocks, as above, keep them out of the build log.
Each stage that sets its own agent starts on a fresh workspace, so files from the Test stage are not on the other agents. Here that is fine because the later stages check out the code themselves. Use stash/unstash if you need to pass build output between stages.

Jenkinsfile: Maven app

pipeline {
  agent none

  options {
    timestamps()
    disableConcurrentBuilds()
    timeout(time: 40, unit: 'MINUTES')
  }

  environment {
    ACR   = 'myacr'
    APP   = 'java-service'
    IMAGE = "${ACR}.azurecr.io/${APP}:${BUILD_NUMBER}"
  }

  stages {
    stage('Build and test') {
      agent {
        docker {
          image 'maven:3.9-eclipse-temurin-17'
          args  '-v $HOME/.m2:/root/.m2'     // cache dependencies between builds
        }
      }
      steps {
        sh 'mvn -B -ntp verify'
      }
      post {
        always {
          junit 'target/surefire-reports/*.xml'
        }
        success {
          archiveArtifacts artifacts: 'target/*.jar', fingerprint: true
        }
      }
    }

    stage('Image and deploy') {
      agent any
      when { branch 'main' }
      steps {
        withCredentials([usernamePassword(credentialsId: 'azure-sp',
                         usernameVariable: 'AZ_ID', passwordVariable: 'AZ_SECRET')]) {
          sh '''
            az login --service-principal -u "$AZ_ID" -p "$AZ_SECRET" --tenant "$AZ_TENANT" --output none
            az acr login --name "$ACR"
            docker build -t "$IMAGE" .
            docker push "$IMAGE"
            az aks get-credentials -n aks-uat -g rg-uat --overwrite-existing
            kubectl -n uat set image deployment/"$APP" "$APP"="$IMAGE"
            kubectl -n uat rollout status deployment/"$APP" --timeout=180s
          '''
        }
      }
    }
  }

  post {
    failure { echo 'Pipeline failed' }
    always  { cleanWs() }
  }
}

If your Jenkins has the Maven Integration plugin and a configured tool named maven-3.9, you can use it instead of a container:

agent any
tools { maven 'maven-3.9'; jdk 'jdk-17' }
steps { sh 'mvn -B verify' }

Jenkinsfile: many apps

One root Jenkinsfile that builds only the apps that changed, in parallel.

// true on the first build, or when files under path changed since the last successful build
def changed(String path) {
  def base = env.GIT_PREVIOUS_SUCCESSFUL_COMMIT
  if (!base) { return true }
  return sh(script: "git diff --name-only ${base} ${env.GIT_COMMIT} -- ${path} | grep -q .",
            returnStatus: true) == 0
}

pipeline {
  agent any
  options { timestamps(); disableConcurrentBuilds() }

  stages {
    stage('Detect changes') {
      steps {
        script {
          env.NODE_CHANGED = changed('apps/node-api').toString()
          env.JAVA_CHANGED = changed('apps/java-service').toString()
        }
      }
    }

    stage('Build changed apps') {
      parallel {

        stage('node-api') {
          when { expression { env.NODE_CHANGED == 'true' } }
          agent { docker { image 'node:20-alpine' } }
          steps {
            dir('apps/node-api') {
              sh 'npm ci'
              sh 'npm test --if-present'
            }
          }
        }

        stage('java-service') {
          when { expression { env.JAVA_CHANGED == 'true' } }
          agent { docker { image 'maven:3.9-eclipse-temurin-17'; args '-v $HOME/.m2:/root/.m2' } }
          steps {
            dir('apps/java-service') {
              sh 'mvn -B -ntp verify'
            }
          }
          post { always { junit 'apps/java-service/target/surefire-reports/*.xml' } }
        }

      }
    }
  }
}
Change detection runs in its own stage on a normal agent (where git is installed) and stores the result in environment variables. The container stages then just read those flags. If the diff fails for lack of history, enable a full (non-shallow) clone in the job's checkout options. The first build of a branch builds everything.

Alternative: keep one Jenkinsfile per app and create a Multibranch Pipeline job per app, each pointing at its own script path (apps/node-api/Jenkinsfile). This is the simplest option when the apps are deployed independently.

Jenkins setup notes

  • Plugins: Pipeline, Git, Docker Pipeline, Credentials Binding, JUnit, GitHub Branch Source (and Blue Ocean if you like the UI).
  • Agent needs: Docker, and az / kubectl installed for deploy stages.
  • Create the job: New Item, Multibranch Pipeline, add the GitHub repo, set the script path.
  • Trigger on push: add a GitHub webhook to https://YOUR_JENKINS/github-webhook/ and enable "GitHub hook trigger" in the job, or poll SCM as a fallback.
  • Credentials: Manage Jenkins, Credentials. Keep the service principal secret there, never in the Jenkinsfile.
  • Backup: back up JENKINS_HOME (jobs, credentials, config) on a schedule.
