What you will build

Cluster
1 AKS cluster, Free tier, Azure CNI Overlay networking, Microsoft Entra ID + Azure RBAC for access
Node pools
1 system pool (add-ons) and 1 user pool (your apps), both with autoscaling
Registry
Azure Container Registry, attached to the cluster so nodes can pull images
App
A small Node.js API with 2+ pods, Service, Ingress, HPA and PodDisruptionBudget
Pipeline
GitHub Actions with OIDC login: build, push, deploy, check health, roll back on failure
Time
About 60 to 90 minutes the first time. Cluster creation itself takes 5 to 10 minutes.
Cost warning: the node VMs are what you pay for. The Free tier control plane has no charge. Delete the resource group when you finish practising (see Day-2). Check the Azure pricing calculator for your region and VM size. Also, AKS Automatic is a newer mode that picks many of these settings for you. This guide uses standard AKS so you learn each building block.

Prerequisites and tools

2.1

Check your Azure account and permissions

You need to create resources and also assign roles, so the right permissions matter.

  • An Azure subscription (a free trial or pay-as-you-go works).
  • Role on the subscription: Owner, or Contributor plus User Access Administrator. Plain Contributor cannot create role assignments, and you need them in Part 11.
  • Enough vCPU quota in your region for the VM size you pick. A new free account often has a low limit.
  • A GitHub account and permission to create a repository.
2.2

Install the command-line tools

Everything below uses these four tools. Cloud Shell in the Azure portal already has them, which is the quickest way to start.

# Windows (PowerShell)
winget install -e --id Microsoft.AzureCLI
winget install -e --id Kubernetes.kubectl
winget install -e --id Helm.Helm
winget install -e --id Git.Git

# macOS
brew install azure-cli kubectl helm git

# Ubuntu / Debian
curl -sL https://aka.ms/InstallAzureCLIDeb | sudo bash
sudo snap install kubectl --classic
sudo snap install helm --classic
# verify (open a NEW terminal first)
az version
kubectl version --client
helm version --short
git --version
Which shell? Commands below are written for Bash (Azure Cloud Shell, WSL, Git Bash, macOS, Linux). In Windows PowerShell, write variables as $RG="rg-aks-demo" and use the backtick ` instead of \ at the end of a line.
2.3

Register the Azure resource providers

A subscription must have each service's provider registered before it can create those resources. New subscriptions sometimes do not.

az provider register --namespace Microsoft.ContainerService
az provider register --namespace Microsoft.ContainerRegistry
az provider register --namespace Microsoft.OperationalInsights
az provider register --namespace Microsoft.Insights
az provider register --namespace Microsoft.Network
az provider register --namespace Microsoft.Compute

# check the state (wait until all say Registered)
az provider list --query "[?namespace=='Microsoft.ContainerService' || namespace=='Microsoft.ContainerRegistry'].{ns:namespace,state:registrationState}" -o table
Portal steps
  1. Open the Azure portal and search Subscriptions.
  2. Click your subscription.
  3. In the left menu under Settings, choose Resource providers.
  4. Search for Microsoft.ContainerService, select it and press Register. Repeat for the others.
  5. Wait until the status shows Registered.

Variables, sign-in and resource group

3.1

Sign in and pick the subscription

az login
az account list -o table                       # find the subscription you want
az account set --subscription "YOUR SUBSCRIPTION NAME OR ID"
az account show -o table                       # confirm it

If you use Cloud Shell you are already signed in.

3.2

Choose names and save them as variables

You will reuse these names in many commands. Setting them once avoids typos. ACR names must be globally unique, lowercase letters and numbers only, 5 to 50 characters.

LOC=centralindia              # pick a region close to your users
RG=rg-aks-demo
ACR=acrdemo12345              # CHANGE: must be unique worldwide
AKS=aks-demo
NS=demo                       # Kubernetes namespace for the app
APP=hello-api
SUB_ID=$(az account show --query id -o tsv)
echo "$SUB_ID"
Variables live only in the current terminal window. If you close it, run this block again.
3.3

Check VM size availability and quota

The most common failure is a VM size that is not offered in the region, or not enough vCPU quota.

# is the size available in your region?
az vm list-skus -l $LOC --size Standard_D2s_v5 --query "[].{name:name,restrictions:restrictions[0].reasonCode}" -o table

# how much quota do you have? (look at the DSv5 line: limit vs current usage)
az vm list-usage -l $LOC --query "[?contains(name.value,'DSv5') || name.value=='cores'].{name:name.localizedValue,used:currentValue,limit:limit}" -o table

You need roughly 2 vCPU per node. Two system nodes plus two user nodes is 8 vCPU. If quota is too low, request an increase under Subscriptions → Usage + quotas, or choose a smaller or different VM family.

3.4

Create the resource group

A resource group is the folder that holds everything. Deleting it later removes the whole lab in one command.

az group create -n $RG -l $LOC --tags env=dev project=aks-demo
az group show -n $RG -o table
Portal steps
  1. Search Resource groups in the top bar and open it.
  2. Click Create.
  3. Choose your Subscription.
  4. Type the Resource group name (rg-aks-demo) and pick the Region.
  5. On the Tags tab add env = dev.
  6. Click Review + create, then Create.

Container registry (ACR)

4.1

Create the registry

AKS pulls your app images from here. Basic is enough for learning. Use Standard or Premium for production features like geo-replication.

az acr create -n $ACR -g $RG -l $LOC --sku Basic
az acr show -n $ACR --query "{name:name,loginServer:loginServer,sku:sku.name}" -o table
Portal steps
  1. Search Container registries and click Create.
  2. Select the subscription and the resource group rg-aks-demo.
  3. Registry name: your unique name. Location: same region as the cluster.
  4. Pricing plan: Basic.
  5. Review + create, then Create.
Leave the registry admin user disabled. AKS and GitHub will use Azure identities with roles instead of a shared password.

Plan the cluster: nodes and networking

Decide these once, so you understand each flag in the next part.

DecisionChoice in this guideWhy
Pricing tierFreeNo control plane charge. Use Standard for production (uptime SLA).
Network pluginAzure CNI OverlayPods get private overlay IPs, so you do not use up VNet addresses. Simple and scalable.
IdentityManaged identityNo service principal secrets to rotate.
Access controlMicrosoft Entra ID + Azure RBACControl who can use the cluster with Azure roles instead of kubeconfig admin files.
Node poolsSystem + UserSystem pool runs cluster add-ons. User pool runs your apps. This keeps your workloads from starving cluster services.
VM sizeStandard_D2s_v5 (2 vCPU, 8 GB)Good general-purpose size. For tiny labs a B-series (for example Standard_B2s) is cheaper but not for production.
ScalingCluster autoscaler on both poolsNodes are added and removed with demand.
ZonesSpread across zones where the region supports themSurvives a datacentre outage. Check that your region has zones.
Workload identityEnabledLets pods use Azure identities without secrets, if you need it later.

Create the AKS cluster

6.1

Create the cluster with the CLI

One command creates the control plane and the first (system) node pool, and attaches the registry.

az aks create \
  --resource-group $RG \
  --name $AKS \
  --location $LOC \
  --tier free \
  --nodepool-name system \
  --node-count 2 \
  --node-vm-size Standard_D2s_v5 \
  --enable-cluster-autoscaler --min-count 2 --max-count 3 \
  --zones 1 2 3 \
  --network-plugin azure --network-plugin-mode overlay --pod-cidr 192.168.0.0/16 \
  --enable-managed-identity \
  --enable-aad --enable-azure-rbac \
  --enable-oidc-issuer --enable-workload-identity \
  --attach-acr $ACR \
  --generate-ssh-keys \
  --tags env=dev project=aks-demo
FlagMeaning
--nodepool-name systemName of the first pool. Lowercase letters and numbers, up to 12 characters.
--enable-cluster-autoscaler --min-count --max-countNode count moves between 2 and 3 with demand.
--zones 1 2 3Spread nodes across availability zones. Remove this flag if your region has no zones.
--network-plugin azure --network-plugin-mode overlayAzure CNI Overlay. --pod-cidr is the private pod address range and must not overlap your other networks.
--enable-aad --enable-azure-rbacMicrosoft Entra ID sign-in and Azure RBAC for Kubernetes authorisation.
--enable-oidc-issuer --enable-workload-identityPrepares pod-level Azure identities.
--attach-acrGrants the cluster permission to pull images from your registry (the AcrPull role).

It takes 5 to 10 minutes. When it finishes it prints a JSON summary.

az aks show -g $RG -n $AKS --query "{state:provisioningState,version:kubernetesVersion,tier:sku.tier}" -o table
If it fails with QuotaExceeded or a VM size error, go back to step 3.3. If zones are not supported in your region, remove --zones 1 2 3.
Portal steps (every tab)
  1. Search Kubernetes services and click Create → Kubernetes cluster.
  2. Basics tab:
    • Subscription and Resource group: rg-aks-demo.
    • Cluster preset configuration: Dev/Test for a lab, or Production Standard for real use. This sets sensible defaults.
    • Kubernetes cluster name: aks-demo. Region: your region.
    • Availability zones: select zones 1, 2 and 3 if offered.
    • AKS pricing tier: Free (lab) or Standard (production).
    • Kubernetes version: keep the default.
    • Authentication and Authorization: choose Microsoft Entra ID authentication with Azure RBAC.
  3. Node pools tab:
    • Click the default pool agentpool to edit it. Name it system, node size Standard_D2s_v5, scale method Autoscale, min 2, max 3. Save.
    • Click Add node pool. Name userpool, Mode: User, size Standard_D2s_v5, Autoscale min 1, max 5. Add a label workload = apps. Add.
  4. Networking tab: Network configuration: Azure CNI Overlay. Leave public access on for this guide. For production consider a private cluster.
  5. Integrations tab: Container registry: pick your ACR. Azure Monitor (Container insights) is optional and adds log cost. Turn it off for a lab.
  6. Advanced tab: note the infrastructure resource group MC_.... Azure puts the node VMs and load balancer there. Do not edit its contents by hand.
  7. Tags tab: env = dev.
  8. Review + create: check the summary, then click Create.
  9. Wait for Your deployment is complete, then click Go to resource.
6.2

Confirm the registry is attached

az aks check-acr -g $RG -n $AKS --acr $ACR.azurecr.io

You should see a message that the cluster can pull from the registry.

Give yourself access and connect with kubectl

7.1

Assign yourself the cluster admin role

With Azure RBAC enabled, even the subscription Owner cannot use the cluster until a Kubernetes data role is assigned. Skipping this gives Forbidden errors.

AKS_ID=$(az aks show -g $RG -n $AKS --query id -o tsv)
ME=$(az ad signed-in-user show --query id -o tsv)

az role assignment create --assignee $ME \
  --role "Azure Kubernetes Service RBAC Cluster Admin" --scope $AKS_ID

az role assignment create --assignee $ME \
  --role "Azure Kubernetes Service Cluster User Role" --scope $AKS_ID
Portal steps
  1. Open your AKS cluster and choose Access control (IAM).
  2. Click Add → Add role assignment.
  3. Search for Azure Kubernetes Service RBAC Cluster Admin, select it and click Next.
  4. Members: choose User, group, or service principal, click Select members, pick yourself.
  5. Review + assign.
  6. Repeat for Azure Kubernetes Service Cluster User Role.

Role assignments can take a minute or two to apply.

7.2

Get credentials and convert the login for Entra ID

Clusters with Entra ID sign-in use the kubelogin helper so kubectl can use your Azure login.

az aks install-cli                                   # installs kubectl and kubelogin
az aks get-credentials -g $RG -n $AKS --overwrite-existing
kubelogin convert-kubeconfig -l azurecli             # use the az login session

kubectl config current-context
kubectl cluster-info
If az aks install-cli says permission denied on Linux or macOS, run it with sudo. On Windows, run the terminal as administrator, or make sure kubectl and kubelogin are on your PATH.
7.3

Verify the nodes and system pods

kubectl get nodes -o wide
kubectl get pods -A
kubectl get nodes -L agentpool,topology.kubernetes.io/zone

You should see two nodes in Ready state, spread across zones, and pods such as coredns and metrics-server in Running state in kube-system.

Node pools: system and user

8.1

Add a user node pool for your apps

Keep your apps off the system pool, so a noisy app cannot break DNS or metrics for the whole cluster.

az aks nodepool add \
  --resource-group $RG --cluster-name $AKS \
  --name userpool --mode User \
  --node-count 2 --node-vm-size Standard_D2s_v5 \
  --enable-cluster-autoscaler --min-count 1 --max-count 5 \
  --zones 1 2 3 \
  --labels workload=apps
Portal steps
  1. Open the cluster and choose Settings → Node pools.
  2. Click Add node pool.
  3. Node pool name: userpool. Mode: User.
  4. OS SKU: Ubuntu Linux (or Azure Linux). Node size: Standard_D2s_v5.
  5. Scale method: Autoscale, min 1, max 5. Availability zones: 1, 2, 3.
  6. Under Labels add workload = apps.
  7. Click Add.
8.2

Reserve the system pool for system pods (taint)

A taint keeps normal pods away from a node. Only pods that tolerate it, such as cluster add-ons, run there.

az aks nodepool update -g $RG --cluster-name $AKS -n system \
  --node-taints CriticalAddonsOnly=true:NoSchedule

kubectl get nodes -L agentpool
kubectl describe node $(kubectl get nodes -l agentpool=system -o name | head -1) | grep -A2 Taints
Only do this after the user pool exists and is Ready, or your own pods will have nowhere to run. Cluster add-ons already tolerate this taint.
8.3

Check both pools

az aks nodepool list -g $RG --cluster-name $AKS \
  --query "[].{name:name,mode:mode,count:count,vm:vmSize,min:minCount,max:maxCount}" -o table
kubectl get nodes -L agentpool,workload
Optional: a cheap Spot pool for batch or test work 
az aks nodepool add -g $RG --cluster-name $AKS -n spot1 --mode User \
  --priority Spot --eviction-policy Delete --spot-max-price -1 \
  --enable-cluster-autoscaler --min-count 0 --max-count 3 \
  --node-vm-size Standard_D2s_v5 --labels workload=batch \
  --node-taints kubernetes.azure.com/scalesetpriority=spot:NoSchedule

Spot nodes can be taken back by Azure at any time. Use them only for work that can be retried.

Ingress controller and namespace

9.1

Create the application namespace

A namespace groups your app. You will also scope the GitHub pipeline's permissions to just this namespace.

kubectl create namespace $NS
kubectl label namespace $NS env=dev
kubectl get ns
9.2

Install the NGINX ingress controller with Helm

The ingress controller is the single public entry point. It creates one Azure load balancer and routes web traffic to your services.

helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update

helm upgrade --install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx --create-namespace \
  --set controller.replicaCount=2 \
  --set controller.nodeSelector."kubernetes\.io/os"=linux \
  --set controller.service.annotations."service\.beta\.kubernetes\.io/azure-load-balancer-health-probe-request-path"=/healthz
After the system pool is tainted (step 8.2), the controller pods run on the user pool. If they stay Pending, check that the user pool has Ready nodes (kubectl get nodes -L agentpool).
9.3

Wait for the public IP

kubectl get pods -n ingress-nginx
kubectl get svc -n ingress-nginx ingress-nginx-controller -w     # wait until EXTERNAL-IP is not pending
INGRESS_IP=$(kubectl get svc -n ingress-nginx ingress-nginx-controller -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
echo $INGRESS_IP

Pod setup: deploy the app

10.1

Smoke test the cluster with a ready-made image

Prove the cluster, ingress and networking work before you add the pipeline, so later problems point to the pipeline and not the cluster.

kubectl create deployment smoke --image=mcr.microsoft.com/azuredocs/aks-helloworld:v1 -n $NS
kubectl expose deployment smoke --port=80 -n $NS
kubectl create ingress smoke --class=nginx --rule="/=smoke:80" -n $NS
kubectl get pods -n $NS
curl -i http://$INGRESS_IP/

You should get an HTTP 200 page. Then clean it up:

kubectl delete ingress,svc,deployment smoke -n $NS
10.2

Create the app and the Dockerfile

Create a repo folder like this (you will push it to GitHub in Part 11):

aks-demo/
  app/
    server.js
    package.json
    Dockerfile
  k8s/
    deployment.yaml
    service.yaml
    ingress.yaml
    hpa.yaml
    pdb.yaml
  .github/workflows/deploy-aks.yml
const http = require("http");
const port = process.env.PORT || 3000;

const server = http.createServer((req, res) => {
  if (req.url === "/health") {
    res.writeHead(200, { "Content-Type": "application/json" });
    return res.end(JSON.stringify({ status: "ok" }));
  }
  res.writeHead(200, { "Content-Type": "text/plain" });
  res.end(`Hello from AKS, pod ${process.env.HOSTNAME}\n`);
});

server.listen(port, () => console.log(`Listening on ${port}`));
process.on("SIGTERM", () => server.close(() => process.exit(0)));
{
  "name": "hello-api",
  "version": "1.0.0",
  "main": "server.js",
  "scripts": { "start": "node server.js" }
}
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install --omit=dev
COPY . .
EXPOSE 3000
USER node
CMD ["node", "server.js"]

More on Dockerfiles is on the Docker page.

10.3

Write the Kubernetes manifests (pod setup)

These files describe how pods run: how many, how much CPU and memory, how health is checked, and where they are placed.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-api
  labels: { app: hello-api }
spec:
  replicas: 2
  revisionHistoryLimit: 5
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  selector:
    matchLabels: { app: hello-api }
  template:
    metadata:
      labels: { app: hello-api }
    spec:
      nodeSelector:
        workload: apps                    # run on the user pool
      topologySpreadConstraints:          # spread pods across nodes
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels: { app: hello-api }
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
      containers:
        - name: hello-api
          image: IMAGE_PLACEHOLDER        # the pipeline replaces this
          ports:
            - containerPort: 3000
          env:
            - name: PORT
              value: "3000"
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { cpu: 500m, memory: 256Mi }
          readinessProbe:
            httpGet: { path: /health, port: 3000 }
            initialDelaySeconds: 3
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /health, port: 3000 }
            initialDelaySeconds: 10
            periodSeconds: 10
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
apiVersion: v1
kind: Service
metadata:
  name: hello-api
spec:
  type: ClusterIP
  selector: { app: hello-api }
  ports:
    - port: 80
      targetPort: 3000
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: hello-api
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: hello-api
                port: { number: 80 }
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hello-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hello-api
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: hello-api
spec:
  minAvailable: 1
  selector:
    matchLabels: { app: hello-api }
SettingWhat it does
nodeSelector workload: appsPlaces pods on the user pool you labelled in step 8.1.
requests / limitsRequests reserve capacity for scheduling. Limits cap use. The HPA measures CPU against the request.
readinessProbeTraffic is only sent to a pod once this passes.
livenessProbeRestarts a pod that stops responding.
maxUnavailable: 0Rolling updates never drop below the desired count, so no downtime.
PodDisruptionBudgetNode upgrades and drains keep at least one pod running.
runAsNonRoot, readOnlyRootFilesystemBasic container hardening.

Test the deployment by hand once (optional but recommended)

Connect GitHub Actions

The pipeline signs in to Azure with OIDC: GitHub gives each run a short-lived token and Azure trusts it. There is no client secret to store or rotate.

11.1

Create the GitHub repository and push the code

cd aks-demo
git init -b main
git add .
git commit -m "AKS demo app"
# create an empty repo on github.com first (for example YOUR_USER/aks-demo), then:
git remote add origin https://github.com/YOUR_USER/aks-demo.git
git push -u origin main

Use a private repo if the code is not meant to be public.

11.2

Create an identity for GitHub in Microsoft Entra ID

This is the "app registration" that represents your pipeline in Azure.

GH_REPO=YOUR_USER/aks-demo
APP_NAME=gh-aks-demo

az ad app create --display-name $APP_NAME
APP_ID=$(az ad app list --display-name $APP_NAME --query "[0].appId" -o tsv)
APP_OBJ=$(az ad app list --display-name $APP_NAME --query "[0].id" -o tsv)
az ad sp create --id $APP_ID
TENANT_ID=$(az account show --query tenantId -o tsv)
echo "client id: $APP_ID   tenant: $TENANT_ID"
Portal steps
  1. Search Microsoft Entra ID → App registrations → New registration.
  2. Name it gh-aks-demo, leave the defaults and click Register.
  3. Copy the Application (client) ID and Directory (tenant) ID from the Overview page.
11.3

Trust your GitHub repo (federated credential)

This tells Azure: accept tokens from this exact repository and environment, and nobody else. The subject must match exactly or login fails.

# for the production environment used in the workflow
az ad app federated-credential create --id $APP_OBJ --parameters '{
  "name": "gh-env-production",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:'$GH_REPO':environment:production",
  "audiences": ["api://AzureADTokenExchange"]
}'

# for the build job, which runs without an environment on the main branch
az ad app federated-credential create --id $APP_OBJ --parameters '{
  "name": "gh-branch-main",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:'$GH_REPO':ref:refs/heads/main",
  "audiences": ["api://AzureADTokenExchange"]
}'
Portal steps
  1. Open the app registration, then Certificates & secrets → Federated credentials → Add credential.
  2. Scenario: GitHub Actions deploying Azure resources.
  3. Organization: your GitHub user. Repository: aks-demo.
  4. Entity type: Environment, name production. Add a second credential for Branch = main.
  5. Give each a name and click Add.
11.4

Give the identity the least permissions it needs

Scope each role as narrowly as possible: push to one registry, use one cluster, write to one namespace.

ACR_ID=$(az acr show -n $ACR --query id -o tsv)
SP_OBJ=$(az ad sp show --id $APP_ID --query id -o tsv)      # object id of the new identity
# (using the object id avoids "principal not found" delays right after creation)
SP="--assignee-object-id $SP_OBJ --assignee-principal-type ServicePrincipal"

# 1. push images to the registry
az role assignment create $SP --role AcrPush --scope $ACR_ID

# 2. fetch cluster credentials
az role assignment create $SP --role "Azure Kubernetes Service Cluster User Role" --scope $AKS_ID

# 3. deploy only inside the demo namespace
az role assignment create $SP --role "Azure Kubernetes Service RBAC Writer" --scope "$AKS_ID/namespaces/$NS"

# 4. read the ingress service (to find the public IP for the smoke test)
az role assignment create $SP --role "Azure Kubernetes Service RBAC Reader" --scope "$AKS_ID/namespaces/ingress-nginx"
The pipeline builds with Docker and pushes, which needs only AcrPush. The az acr build command used in step 10.4 runs a cloud build task, which needs more rights (for example Contributor on the registry), so it is not used in the pipeline. If a manifest is rejected as Forbidden, check what it creates, or temporarily use RBAC Cluster Admin to confirm it is a permissions issue.
11.5

Add the repository variables to GitHub

The client, tenant and subscription IDs are identifiers, not passwords, so repository variables are fine.

gh auth login                                   # once, if you have not used the GitHub CLI
gh variable set AZURE_CLIENT_ID       --body "$APP_ID"   --repo $GH_REPO
gh variable set AZURE_TENANT_ID       --body "$TENANT_ID" --repo $GH_REPO
gh variable set AZURE_SUBSCRIPTION_ID --body "$SUB_ID"   --repo $GH_REPO
GitHub web steps
  1. Open your repo on github.com → Settings.
  2. Left menu: Secrets and variables → Actions.
  3. Open the Variables tab and click New repository variable.
  4. Add AZURE_CLIENT_ID, AZURE_TENANT_ID and AZURE_SUBSCRIPTION_ID with the values from the earlier steps.
11.6

Create the production environment with an approval gate

  1. Repo → Settings → Environments → New environment.
  2. Name it exactly production (it must match the federated credential).
  3. Tick Required reviewers and add yourself or your team. Save protection rules.
  4. Optional: restrict Deployment branches to main.
Environment protection rules on private repos need a paid GitHub plan. On a free private repo, skip the reviewers and the pipeline still works. The environment name must still match the federated credential subject.
11.7

Add the workflow file

This is the pipeline: build the image and push it to ACR, then deploy to AKS, check health, and roll back if the check fails.

name: deploy-aks

on:
  push:
    branches: [main]
    paths: ["app/**", "k8s/**", ".github/workflows/deploy-aks.yml"]
  workflow_dispatch:

permissions:
  id-token: write      # needed for OIDC login to Azure
  contents: read

concurrency:
  group: deploy-aks
  cancel-in-progress: false

env:
  ACR_NAME: acrdemo12345     # CHANGE to your registry name
  AKS_NAME: aks-demo
  RESOURCE_GROUP: rg-aks-demo
  NAMESPACE: demo
  APP: hello-api

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      image: ${{ steps.meta.outputs.image }}
    steps:
      - uses: actions/checkout@v4

      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Compute image name
        id: meta
        run: echo "image=${ACR_NAME}.azurecr.io/${APP}:${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"

      - name: Build and push image
        run: |
          az acr login --name "$ACR_NAME"
          docker build -t "${{ steps.meta.outputs.image }}" ./app
          docker push "${{ steps.meta.outputs.image }}"

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4

      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Connect to AKS
        run: |
          sudo az aks install-cli
          az aks get-credentials -g "$RESOURCE_GROUP" -n "$AKS_NAME" --overwrite-existing
          kubelogin convert-kubeconfig -l azurecli
          kubectl get pods -n "$NAMESPACE"

      - name: Deploy manifests
        run: |
          sed -i "s|IMAGE_PLACEHOLDER|${{ needs.build.outputs.image }}|" k8s/deployment.yaml
          kubectl apply -n "$NAMESPACE" -f k8s/

      - name: Wait for rollout
        run: kubectl rollout status deployment/"$APP" -n "$NAMESPACE" --timeout=180s

      - name: Smoke test through the ingress
        run: |
          IP=$(kubectl get svc -n ingress-nginx ingress-nginx-controller -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
          echo "ingress ip: $IP"
          curl -fsS --retry 6 --retry-delay 5 "http://$IP/health"

      - name: Roll back if anything failed
        if: failure()
        run: |
          kubectl rollout undo deployment/"$APP" -n "$NAMESPACE" || true
          kubectl rollout status deployment/"$APP" -n "$NAMESPACE" --timeout=120s || true
How the identity flows: permissions: id-token: write lets the job request a GitHub token. azure/login exchanges it for an Azure token using your federated credential. The deploy job uses environment: production, so Azure sees the subject repo:...:environment:production.
The smoke test reads the ingress service in the ingress-nginx namespace. That is why step 11.4 gives the pipeline a read-only role on that namespace. Also note that cluster-wide commands such as kubectl get ns are not allowed for a namespace-scoped role, so the workflow only uses namespaced commands.

Confirm the image tag matches the first 7 characters of the commit that triggered the run. That proves the pipeline, not your laptop, deployed it.

12.3

Make a change and watch it roll out

# edit app/server.js (for example change the greeting), then:
git add -A && git commit -m "Change greeting" && git push

Pods are replaced one at a time. With maxUnavailable: 0 and a readiness probe, users see no downtime.

12.4

Try a rollback and load-based scaling

kubectl rollout history deployment/hello-api -n $NS
kubectl rollout undo deployment/hello-api -n $NS

# watch the autoscaler (generate load from a temporary pod)
kubectl get hpa -n $NS -w
kubectl run load --rm -it --image=busybox:1.36 -n $NS -- sh -c "while true; do wget -q -O- http://hello-api/ > /dev/null; done"

Stop the load with Ctrl+C. The HPA scales the pods back down after the stabilisation window. See the HPA vs VPA page for how this works.

Day-2: upgrades, cost, cleanup

Upgrades

az aks get-upgrades -g $RG -n $AKS -o table
az aks upgrade -g $RG -n $AKS --kubernetes-version NEW_VERSION        # control plane + nodes
az aks nodepool upgrade -g $RG --cluster-name $AKS -n userpool --node-image-only   # OS image only

Upgrade a test cluster first. PodDisruptionBudgets keep your app available while nodes are drained one by one. You can also set an automatic upgrade channel: az aks update -g $RG -n $AKS --auto-upgrade-channel patch.

Save cost on non-production

az aks stop  -g $RG -n $AKS      # stops the nodes and the compute charge
az aks start -g $RG -n $AKS
az aks nodepool scale -g $RG --cluster-name $AKS -n userpool --node-count 1   # only works with autoscaler off
  • Set resource requests from real usage. Over-requesting is the biggest source of waste.
  • Use the cluster autoscaler min counts as low as is safe, and Spot pools for retryable work.
  • Tag everything and use Cost Management budgets. See the service picker FinOps tips.

Monitoring

az aks enable-addons -g $RG -n $AKS --addons monitoring     # Container insights (adds Log Analytics cost)
kubectl top nodes
kubectl top pods -n $NS

Delete everything when you are done

az group delete -n $RG --yes --no-wait                       # cluster, registry, node resource group
az ad app delete --id $APP_ID                                 # the GitHub identity
Check afterwards: in the portal, open Resource groups and confirm both rg-aks-demo and the MC_... group are gone. Leftover node VMs and public IPs keep billing.
