GUIDE 06

Linux server migration: commands and automation

Move an application server (web, app, database) to a new Linux host with minimal downtime: assess, prepare, sync, cut over, verify, roll back.

Migration plan

PhaseGoalDowntime?
AssessInventory OS, packages, services, cron, ports, data sizeNo
PrepareBuild target, install same stack, lower DNS TTLNo
Initial syncCopy bulk data while source is liveNo
Final sync + DBFreeze writes, copy the delta, dump/restore DBShort window
CutoverSwitch DNS / load balancer to targetSeconds
Verify and watchTest, monitor, keep source ready for rollbackNo
Always take a backup or snapshot of the source first, and rehearse the whole procedure on UAT before touching production.

1. Assess the source

cat /etc/os-release; uname -r; hostname -f
lscpu | head -20; free -h; df -hT; lsblk
ip -br a; ss -tulpn                       # IPs and listening ports
systemctl list-units --type=service --state=running
dpkg -l > packages.txt                    # Debian/Ubuntu
rpm -qa > packages.txt                    # RHEL/CentOS
crontab -l; ls /etc/cron.*; cat /etc/crontab
cat /etc/fstab; cat /etc/hosts
ls /etc/nginx /etc/apache2 /etc/httpd 2>/dev/null
du -sh /var/www /opt /home /var/lib/mysql /var/lib/postgresql 2>/dev/null
getent passwd | awk -F: '$3>=1000{print $1}'   # human users
sudo iptables -S; sudo ufw status

2. Prepare the target

# same OS family and versions where possible
sudo apt update && sudo apt -y upgrade
sudo apt install -y nginx mysql-server rsync   # match source stack

# re-create users with the same UID/GID so file ownership stays correct
sudo groupadd -g 1001 deploy
sudo useradd  -m -u 1001 -g 1001 -s /bin/bash deploy

# passwordless SSH from target to source for rsync
ssh-keygen -t ed25519 -f ~/.ssh/migrate -N ""
ssh-copy-id -i ~/.ssh/migrate.pub user@SOURCE_IP

# lower DNS TTL to 300s a day or two before cutover

3. Sync files with rsync

# dry run first
rsync -aHAXzn --info=progress2 -e "ssh -i ~/.ssh/migrate" \
  user@SOURCE_IP:/var/www/ /var/www/

# initial sync (source still live)
sudo rsync -aHAXz --info=progress2 --numeric-ids -e "ssh -i ~/.ssh/migrate" \
  --rsync-path="sudo rsync" user@SOURCE_IP:/var/www/ /var/www/

# configs
sudo rsync -aHAXz -e "ssh -i ~/.ssh/migrate" --rsync-path="sudo rsync" \
  user@SOURCE_IP:/etc/nginx/ /etc/nginx/
FlagMeaning
-aArchive: recursive, preserve perms, times, owners, symlinks
-H -A -XKeep hard links, ACLs, extended attributes
-zCompress during transfer
-nDry run
--numeric-idsKeep raw UID/GID, not name mapping
--deleteRemove files at target that no longer exist at source (use only on the final sync)

Run the same rsync again at cutover time. It copies only what changed, so the final window is short.

4. Migrate databases

MySQL / MariaDB

# on source: consistent dump without locking InnoDB tables
mysqldump --single-transaction --routines --triggers --events \
  --all-databases -u root -p | gzip > all.sql.gz

# copy and restore
scp all.sql.gz user@TARGET_IP:/tmp/
gunzip -c /tmp/all.sql.gz | mysql -u root -p

PostgreSQL

pg_dump -Fc -U postgres appdb -f appdb.dump          # one database
pg_dumpall -U postgres --globals-only > globals.sql  # roles
scp appdb.dump globals.sql user@TARGET_IP:/tmp/

psql -U postgres -f /tmp/globals.sql
createdb -U postgres appdb
pg_restore -U postgres -d appdb -j 4 /tmp/appdb.dump

Check the data matches

mysql -e "SELECT table_schema, SUM(table_rows) FROM information_schema.tables GROUP BY 1;"
psql -d appdb -c "SELECT relname, n_live_tup FROM pg_stat_user_tables ORDER BY 1;"
For near-zero downtime on large databases, set up replication (MySQL replica or PostgreSQL streaming/logical replication) and promote the target at cutover instead of dump and restore.

5. Cutover

  1. Announce the maintenance window.
  2. Stop the app on the source (or put it in read-only/maintenance mode).
  3. Run the final rsync and the final database dump/restore.
  4. Start services on the target: sudo systemctl enable --now nginx mysql app.
  5. Test on the target before switching, by forcing the hostname locally: 
    curl -s --resolve example.com:443:TARGET_IP https://example.com/health -k
  6. Switch DNS (A record) or the load balancer backend to the target.
  7. Keep the source stopped but intact for the rollback period.

6. Verify

systemctl --failed
ss -tulpn | grep -E ':80|:443|:3306|:5432'
journalctl -u nginx -u app --since "10 min ago" --no-pager
curl -fsS https://example.com/health
dig +short example.com
tail -f /var/log/nginx/error.log
sudo crontab -l -u deploy
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | openssl x509 -noout -dates

Automation script

A reusable Bash script run from the target. It does a dry run unless you pass --apply, and it logs everything.

#!/usr/bin/env bash
# Usage: ./migrate.sh --source user@10.0.0.5 [--apply]
set -euo pipefail

SOURCE=""; APPLY=0
while [[ $# -gt 0 ]]; do
  case "$1" in
    --source) SOURCE="$2"; shift 2 ;;
    --apply)  APPLY=1; shift ;;
    *) echo "unknown arg $1"; exit 1 ;;
  esac
done
[[ -z "$SOURCE" ]] && { echo "--source required"; exit 1; }

KEY="$HOME/.ssh/migrate"
LOG="/var/log/migrate-$(date +%F-%H%M).log"
PATHS=("/var/www" "/etc/nginx" "/opt/app")
DB_DUMP="/tmp/all-$(date +%F).sql.gz"
RSYNC_OPTS=(-aHAXz --numeric-ids --info=stats1 -e "ssh -i $KEY" --rsync-path="sudo rsync")
[[ $APPLY -eq 0 ]] && RSYNC_OPTS+=(-n)

exec > >(tee -a "$LOG") 2>&1
echo "== $(date) migrate from $SOURCE (apply=$APPLY) =="

for p in "${PATHS[@]}"; do
  echo "-- syncing $p"
  sudo mkdir -p "$p"
  sudo rsync "${RSYNC_OPTS[@]}" "$SOURCE:$p/" "$p/"
done

if [[ $APPLY -eq 1 ]]; then
  echo "-- dumping database on source"
  ssh -i "$KEY" "$SOURCE" \
    "sudo mysqldump --single-transaction --routines --triggers --events --all-databases | gzip" > "$DB_DUMP"
  echo "-- restoring database"
  gunzip -c "$DB_DUMP" | sudo mysql
  echo "-- restarting services"
  sudo systemctl restart nginx
  curl -fsS http://localhost/health && echo "health OK"
else
  echo "Dry run complete. Re-run with --apply to copy for real."
fi
echo "== done, log: $LOG =="
chmod +x migrate.sh
./migrate.sh --source ubuntu@10.0.0.5            # rehearsal
./migrate.sh --source ubuntu@10.0.0.5 --apply

Schedule an incremental sync before cutover day, so the final delta is small:

crontab -e
0 */6 * * * /home/ubuntu/migrate.sh --source ubuntu@10.0.0.5 --apply >> /var/log/migrate-cron.log 2>&1
The cron entry above re-imports the database every run. Use it for file sync only, and keep the database step manual or drop the --apply DB part for scheduled runs.

Automation with Ansible

Use Ansible to build the target identically each time, then rsync the data. See Ansible basics.

---
- name: Prepare migration target
  hosts: target
  become: true
  vars:
    app_user: deploy
    app_uid: 1001
    packages: [nginx, mysql-server, rsync, curl, ufw]
  tasks:
    - name: Install packages
      ansible.builtin.apt:
        name: "{{ packages }}"
        state: present
        update_cache: true

    - name: Create group with matching GID
      ansible.builtin.group:
        name: "{{ app_user }}"
        gid: "{{ app_uid }}"

    - name: Create user with matching UID
      ansible.builtin.user:
        name: "{{ app_user }}"
        uid: "{{ app_uid }}"
        group: "{{ app_user }}"
        shell: /bin/bash

    - name: Sync web root from source
      ansible.posix.synchronize:
        src: /var/www/
        dest: /var/www/
        mode: pull
        rsync_opts: ["--numeric-ids"]
      delegate_to: "{{ inventory_hostname }}"

    - name: Allow SSH and web
      community.general.ufw:
        rule: allow
        port: "{{ item }}"
        proto: tcp
      loop: ["22", "80", "443"]

    - name: Enable firewall
      community.general.ufw:
        state: enabled

    - name: Services enabled and started
      ansible.builtin.service:
        name: "{{ item }}"
        state: started
        enabled: true
      loop: [nginx, mysql]
The synchronize pull needs the target to reach the source over SSH. For a one-way copy, running rsync directly (as in the script) is simpler and easier to debug.

Rollback

  • Point DNS / the load balancer back at the source (low TTL makes this fast).
  • Start the application on the source again.
  • If writes happened on the target after cutover, dump those changes and apply them back to the source before reopening.
  • Keep the source untouched for at least a few days after a successful migration.

Checklist

  • Backup or snapshot of source taken and restore tested
  • Target OS, packages and versions match (or differences are known)
  • UIDs/GIDs, cron jobs, systemd units, /etc/hosts, firewall rules copied
  • SSL certificates and renewal job moved (Certbot / cert files)
  • Environment files and secrets transferred securely
  • DNS TTL lowered ahead of time
  • Monitoring, log shipping and backups configured on the new host
  • Rollback plan written and agreed
  • Rehearsal done on UAT with timings recorded
