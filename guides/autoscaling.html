What you just watched

  • HPA looks at average CPU across pods. When it passes the target (70% here), it adds replicas. Quiet traffic removes them again, but slowly, using a stabilization window so it does not flap.
  • VPA keeps the replica count and changes the resource requests of each pod. In the classic mode it must evict and recreate a pod to apply new numbers. That is the grey blinking pod: while it restarts, the other pod carries extra load.
  • HPA never touches running pods. VPA does, so give services enough replicas that one restart is safe.

HPA in practice

HPA needs the metrics-server (AKS and most managed clusters ship it) and CPU requests on your containers, because utilization is measured against the request.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # wait 5 min before removing pods
    scaleUp:
      policies:
        - type: Percent
          value: 100
          periodSeconds: 60
kubectl autoscale deployment myapp --cpu-percent=70 --min=2 --max=8   # quick version
kubectl get hpa -w
kubectl describe hpa myapp          # shows current vs target and scaling events
kubectl top pods
The replica count HPA wants is roughly ceil(currentReplicas × currentCPU / targetCPU). In the demo, 2 pods at 140% against a 70% target asks for 4.

VPA in practice

VPA is an add-on: install its components first (it is not built into every cluster). Start in recommendation-only mode, read the advice, and only then let it act.

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: myapp
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  updatePolicy:
    updateMode: "Off"          # "Off" = recommend only, "Auto" = apply by recreating pods
  resourcePolicy:
    containerPolicies:
      - containerName: "*"
        minAllowed: { cpu: 100m, memory: 128Mi }
        maxAllowed: { cpu: "2", memory: 2Gi }
kubectl describe vpa myapp          # Recommendation: lower bound, target, upper bound
kubectl get vpa myapp -o jsonpath='{.status.recommendation.containerRecommendations}'
Using VPA in Off mode is a safe way to right-size requests from real usage, which also cuts cloud cost. Newer Kubernetes versions add options to resize some resources without recreating the pod. Check what your version and VPA release support before relying on it.

Pods are not enough: the node layer

HPA adds pods, but pods still need room on a node. If the nodes are full, new pods sit in Pending until the Cluster Autoscaler (or AKS node-pool autoscaling) adds a node.

# AKS: let the node pool grow and shrink
az aks nodepool update -g rg-uat --cluster-name aks-uat -n nodepool1 \
  --enable-cluster-autoscaler --min-count 2 --max-count 6

The full chain on a traffic spike: load rises → HPA adds pods → nodes fill up → Cluster Autoscaler adds nodes → pods schedule. See the troubleshooting section when pods stay Pending.
